# adk-prose-revision

## Goal

让成稿更清楚、更紧凑，同时尽可能少改动。优先照顾读者理解、表达准确与作者原有风格，而不是追求“看起来不像 AI”的分数。

## When to run

- 只在用户明确要求对已有自然语言文稿做表达检查或润色，且此可选 Skill 已显式选择/安装时使用。
- 仅要求“检查、评估、指出问题”时，进入 report 模式：不写回正文。
- 明确要求“润色、改写、优化表达”时，进入 revise 模式：可直接交付改稿，不额外增加批准轮次。若用户同时要求“先给建议不要修改”，则优先 report。
- 原创初稿、资料查证、架构决策、代码/配置审查由相应能力处理。技术报告仅改语言，不代替技术事实审查。

## Workflow

1. **冻结边界**：识别受众、文稿用途、口吻、风格参考和禁改项。缺风格文件时保持原稿语气；不要凭空模拟作者。
2. **定位问题**：只提能指向原句、解释读者困扰的候选，例如重复铺垫、主体不明、同一实体反复换称呼、过长修饰、空洞强调、刻板句式连续堆叠。判断具体语境，正常对比、列表、专业术语和有意修辞不算错误。
3. **谨慎筛选**：候选分别标记“值得改 / 保留 / 不确定”。改动不能明确改善可读性、或可能损害技术含义时保留；不使用禁词清单、标点次数或段落长短作为强制改写规则。
4. **按请求交付**：report 模式给出少量最重要的“位置—原文—问题—建议”，同时说明保留项；revise 模式仅修改已确认安全的局部，交付改稿和精简变更说明。用户要求文件写回时，遵守宿主的文件权限和审批边界。
5. **核对差异**：复读修改前后对应语句，确认实体、数值与单位、因果、程度词（可能/通常/必须）、引用、段落和列表结构保持一致。发现事实不确定时标记待核，不替用户补事实。

## Guardrails

- 报告中的“更自然”“更像人写的”只是主观编辑意见；不得声称 AI 检测结论、统计显著性或来源模型。
- 避免机械打散句长、强删破折号、改动序号标题或替换全部行业用词；这些操作可能伤害可读性。
- 引号内原文、代码块、接口名、日志、命令行、表格单元格等默认只读；用户明确允许结构调整时也必须保障信息完整。
- 不将原稿、敏感内容或修订对照发送给第三方模型/服务。
- 真实质量改进和 Token 节省必须靠后续同任务对照测量；静态规则检查不代表模型效果已提高。

## Output

- **report**：3–5 个优先发现（没有问题则说明无需改动），每项给原文定位与可执行建议；不输出全量机械命中表。
- **revise**：完整修订稿（长文件按用户的交付方式）+ 最多 5 条关键变化；对无法保证等价的段落原样保留并单独注明。
- 需按具体文体补充反例时，按需阅读 references/review-cases.md，默认不加载。

## Stop

输入不足以确定改动是否保真、涉及未经确认的事实或明确要求保持原样时，停止相应修改并说明原因；不为了凑“改写量”而硬改。
