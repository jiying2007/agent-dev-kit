# 中文代码审查规范

## Goal

提供适配国内团队沟通风格的代码审查规范，确保审查意见既有技术深度又兼顾沟通效率。

## Prerequisites
- 确认代码变更（diff）完整且可读。
- 获取最小上下文：变更目的、影响范围。

## 审查维度

| 维度 | 检查项 | 严重性 |
|------|--------|--------|
| 正确性 | 逻辑是否正确、边界是否处理 | Critical |
| 可读性 | 命名是否清晰、注释是否充分 | Important |
| 安全性 | 是否有注入/越权/泄露风险 | Critical |
| 性能 | 是否有性能问题 | Suggestion |
| 规范 | 是否符合团队编码规范 | Suggestion |

## 沟通风格

### 先扬后抑
```
✅ "这个错误处理写得很清晰。不过这里有个边界条件可能没考虑到..."
❌ "这里有个 bug。"
```

### 用建议代替命令
```
 ✅ "建议在这里加个空值检查，防止 NPE。"
❌ "这里必须加空值检查。"
```

### 用提问代替否定
```
✅ "这里的并发安全是怎么考虑的？"
❌ "这里不是线程安全的。"
```

## Workflow
1. 获取完整 diff
2. 按五维度逐项审查
3. 使用先扬后抑风格记录发现
4. 按严重性排序
5. 输出审查报告

## Quality Gate
- 五维度审查全覆盖
- 审查意见使用中文且符合沟通风格
- 发现已按严重性排序

## Evidence Template
```md
- 审查维度覆盖: 5/5
- Critical 发现: N 个
- 审查报告路径: <path>
```

## 合理化借口拦截

| 借口 | 现实 | 正确做法 |
|------|------|---------|
| "代码能跑就行" | 能跑不等于正确 | 按五维度全面审查 |
| "审查太严格影响效率" | 低成本发现问题是审查的价值 | 保持标准不降低 |

## 健壮性规范

- **输入验证**: 确认 diff 完整且可读
- **重试策略**: 审查遗漏时补充检查
- **超时控制**: 单次审查不超过 30 分钟
- **异常隔离**: 某个维度不阻塞其他维度
- **日志记录**: 记录审查发现和建议
