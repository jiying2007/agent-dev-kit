# 交互式设计探索与方案拷问

## Goal
帮助用户厘清真正要解决的问题，通过多轮探索或对抗性追问提升设计质量；不是尽快填写 PRD，也不是复制第二套 Workflow、授权或审批系统。

## Mode selection
- **Explore（默认探索）**：用户说“头脑风暴 / brainstorm / 讨论思路 / 想想怎么做”，或真实意图尚不清晰。一次只问一个能改变方案的核心问题，优先发散、再比较与收敛。
- **Challenge（深度拷问）**：用户说“Grill Me / gill me / grilling / 拷问我的方案 / 挑战方案 / 找盲区”。用依赖决策树逐轮审视假设、反例、极端场景和代价。一次提出当前可独立回答的 frontier（通常 2–4 个问题），每个问题附建议与理由。
- **Fast path（不进入多轮）**：上下文已充分、用户只要直接实现/执行既定计划，退出并交给对应实现或 `adk-requirements-triage`；已有明确任务不以“再确认一次”为停止门。
- 讨论过程中可切换 Explore ↔ Challenge；模式只是同一个 Skill 的行为，不创建新 agent、gate 或 workflow。

## Look before asking
1. 先看用户原话、已有决策/批准、当前代码/文档、限制、测试和历史负结果；复述时区分事实与推断。
2. 能从已有上下文、仓库或可信工具查到的事实自己查，不让用户代替查资料；外部查询不可用则标明未知与影响。
3. 把真正影响设计的未知列为待决节点。对无关、可逆、低风险细节给出可纠正建议，不形式化追问。
4. 用户明确偏好与已有批准优先；建议和默认值始终标为“建议”，不能冒充已确认的用户决策。

## Explore protocol
1. **Why before options**：目标和受益对象尚不清楚时先问一个开放问题，使用用户的语言，不先抛选项诱导；说明答案会改变哪项设计。
2. **Adaptive questioning**：每轮依据最新回答更新问题模型；只问一个最重要、且未被现有材料回答的问题。不要机械遍历清单；用户问“你推荐”就给出具体建议。
3. **Consequences and alternatives**：意图清晰后比较 2–3 个真实可行的架构/方案，说明收益、成本、失败方式和推荐；如果只有一种合理路径，明确说明，不制造伪选项。
4. **Play back**：阶段性回放“已确认事实、用户决策、Agent 建议、未知项”，允许用户纠正；避免每轮整份长文。
5. **Exit**：若用户只要讨论则留在讨论；若设计清晰则形成短设计（Why、目标/非目标、取舍、约束、验收、开放问题），只对改变结果的重大选择请求确认。用户要求跳过追问、直接开工或停止时尊重指令，进入原 ADK 授权与实施流程。

## Challenge protocol — decision tree
1. 根节点定义可证伪的目标、现状与失败定义。每个未决选择保存最小记录：`id / decision / prerequisites / evidence / alternatives / owner / status`；仅留在当前会话状态，不另建持久状态机。
2. **Frontier**：所有依赖已经解决、此刻可以独立回答的决策。未解决依赖的子问题留到后轮；当前独立 frontier 按影响程度提出 2–4 个编号问题，每题给建议与理由；数量更多时分批，不丢分支。
3. 针对实际方案挑战：关键假设、成本、性能、资源、安全、兼容性、维护、极端输入、交接与恢复。用反例和失败预演，不为拷问而拷问。
4. 依据回答更新决策状态：`confirmed / proposed / unresolved / invalidated`。“都按建议”只确认本轮明确的选项，不构成对未来未知事项的无限授权。
5. 有事实依赖时先自行查询；未验证事实保留 blocker，其余独立 frontier 继续。不要诱导用户一律回答“是”；事实不充分时先提开放问题。
6. frontier 为空、重大分支达成共识或用户明确结束时，总结决定、剩余假设、反例验证与实施交接；用户仍在拷问阶段时**不擅自开始实施**。

## Cross-mode convergence and handoff
- **讨论结束不等于开发完成**。只把已确认设计交 `adk-requirements-triage` 固化目标、done-when、验收证据与 blocker；后续继续复用 ADK 的设计、任务、实现和验证。
- 低风险小任务、已经批准的设计或明确要求“直接做”时不得强制多轮访谈/设计文档/重复审批；高风险和不可逆操作仍服从原 Gate。
- **防空转**：连续两轮没有新信息、没有发现新反例且没有关闭决策时，主动指出原因，给出推荐或最小试验；不能无界循环。
- 多个独立子项目先明确优先级，逐个设计树收敛；不要混为一份大 PRD。

## Output contract
Explore 单轮：`已知要点（极简） → 本轮关键问题（一个） → 为什么会改变方案`；需要比较时附 2–3 个真实方案与推荐。
Challenge 单轮：`已确认决策 → frontier Q1..Q4（问题/建议/依据） → 依赖未决项`，等待回答后更新。
交接：`Mode / Goal and why / User-confirmed decisions / Agent proposals / Alternatives & trade-offs / Risks and counterexamples / Open decision IDs / Validation / Next owner`。

## Quality Gate
- 每个问题应解释“答案会改变什么”，否则删除；不可反复索取可查事实或已确认决策。
- Explore 目标不明时不先诱导选项；Challenge 不让未解决依赖进入本轮 frontier；建议与用户决策必须分开。
- 至少识别真实取舍或说明只有单一路径，关键反例有验证路径；不以填完模板代替设计质量。
- 静态路由/格式测试**不证明**多轮交互有效，实际效果依据 `docs/evals/interactive-discovery-evaluation.md` 的模型对照和人工复核。
- 用户改变意图为明确执行时停止额外追问，遵守既有风险及授权边界。
