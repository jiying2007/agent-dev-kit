# 结构化需求提问对齐

## Goal
- 通过结构化提问消除模糊需求，确保在动手实现前对齐理解。

## Prerequisites
- 确认用户能参与需求对齐会话。
- 获取最小上下文：用户原始需求描述。

## 触发条件和最小澄清

- 首先读取用户已给定的范围、此前决策、仓库事实和可用验收标准；禁止重复询问。
- 只把会改变安全边界、不可逆操作、外部授权或验收结论的缺口列为阻塞问题；每轮优先提出一个关键问题。
- 对可逆且低风险的非关键细节，给出明确假设、可用默认值、验证或回退方案并继续。不得将个人偏好推断为用户明确授权。
- 非阻塞问题作为 `assumptions/open_questions` 记录，不能一律阻断实现。

## 提问模板

| 维度 | 问题模板 |
|------|---------|
| 目标 | "这个功能要解决什么问题？" |
| 用户 | "谁会使用这个功能？" |
| 边界 | "什么情况下不需要这个功能？" |
| 验收 | "怎样算做完了？" |
| 约束 | "有什么技术限制？" |

## Workflow

1. 摘要已有需求、明确边界与已知事实，不重复发问。
2. 发散最多 2–3 个可行方向，仅在影响决策时给出取舍。
3. 对缺失的关键阻塞信息提出精准问题；无法互动时输出 `blocked` 与证据，不得猜测权限。
4. 将低风险假设标为 `assumed`，交付最小验收标准与验证路径。
5. 仅在新范围、不可逆操作或风险豁免需要额外审批时请求用户确认；正常明确任务直接继续。
6. 把已收敛要求交给 `adk-requirements-triage` 形成可验证工作包。

## 与 adk-requirements-triage 的区别
- adk-structured-requirements-questioning: 通过结构化提问消除模糊需求
- adk-requirements-triage: 将明确需求转为可验证的工程条目

## Quality Gate
- 每条真正阻塞的问题必须说明对应的验收、安全或授权影响。
- 不得重复询问已经回答的内容；可逆低风险假设可留痕推进。
- 不把用户再次确认作为所有正常开发任务的强制前提。
- 输出可验证的目标、边界、验收和剩余风险。

## Evidence Template
```md
- 模糊点清单: (已对齐 N 个)
- 需要额外授权: yes / no / blocked
- 输出文档路径: <path>
```

## 合理化借口拦截

| 借口 | 现实 | 正确做法 |
|------|------|---------|
| "需求已经很清楚了" | 模糊需求是 bug 的温床 | 按流程逐点确认 |
| "用户说的我都理解了" | 理解偏差很难自我发现 | 复述并请用户确认 |

## 健壮性规范

- **输入验证**: 检查用户描述是否为空或过于模糊
- **重试策略**: 同一问题无新信息则停止重复提问，报告缺口并推进独立工作
- **超时控制**: 只针对阻塞问题提出必要澄清，其他内容直接执行或留痕假设
- **异常隔离**: 某个维度对齐失败不影响其他维度
- **日志记录**: 记录每个模糊点和最终确认结果
