# 深模块架构重构的候选判断

仅在问题是架构局部性而非简单格式/命名时加载。

1. **现实触点**：从实际调用图收集两处以上变更经常一起修改的代码、公共调用方和测试入口。不要凭文件行数或单个长函数判定边界。
2. **深度/杠杆**：接口大小（外部理解负担）相对于隐藏行为复杂度；一个 adapter 可能是假想 seam，第二个真实消费方才可能说明需要共享抽象。
3. **两个设计**：A 沿已有模块局部整理，B 移动稳定 seam/封装状态。为每项列调用方必须知道的前后信息、预计同时修改文件、公开接口断言与回退成本。
4. **验证**：从真实调用方走一次变更：能否只改一个模块、在公开边界运行测试并保留旧行为？判断未来修改的局部性，不通过代码减少行数替代。
5. **拒绝条件**：为了“干净架构”新增只用一次的间接层、框架或术语，没有实证需求时遵守 YAGNI；若尚无测试保护，先缩小可测区域再改。

输出：`change scenario / existing callers / candidate seams / A-vs-B / negative case / public test / maintenance cost / decision`。仅有真实收益的方案进入原有需求/设计授权流程。
