# Agent 详细执行与生命周期规则

本文件承接根 `AGENTS.md` 下沉的详细执行规则。根文件保留每轮立即执行的索引和硬边界；非平凡实现、长任务、失败恢复或 Gate 变更必须继续读取本文件。

## AI 防幻觉与范围控制规则

> 来源：agent-dev-kit 范围控制基线

### R1 上下文与清窗规则

- **R1.1 清窗触发信号**：出现以下任一信号时必须触发清窗：
  1. 输入 token > 50k
  2. AI 复读已说过的内容（自我提示症状）
  3. 同类错误连续出现 ≥ 2 次
  4. 用户感觉对话打转
- **R1.2 阶段切换输出**：阶段切换时必须输出本阶段工件文件，作为后续唯一上下文来源。
- **R1.3 引用历史决策**：引用历史决策必须用 `@文件路径` 形式，禁止粘贴正文复述。
- **R1.4 不允许“我记得”**：所有决策必须可在 `.md` 中查到。
- **R1.5 重启协议**：
  - 清窗前：写 PROGRESS.md（已完成/当前/已排除方案/待确认假设），更新 STATE.md 中断任务字段，输出重启指令。
  - 清窗后：按 METHODOLOGY → RULES → 当前阶段 prompt → CONTEXT → REQUIREMENT → DESIGN → TASK → PROGRESS 顺序加载。
- **R1.6 反重复检查**：清窗恢复后先读 PROGRESS.md 已排除方案；下一步命中时必须解释本次差异，否则停止。
- **R1.7 任务过大信号**：半路触发清窗说明 task 拆分不足；恢复后先拆成至少两个子任务。
- **R1.8 跨任务失败检查**：
  1. 任何 Build 任务先用当前任务关键词检索 `knowledge/L2-domain/lessons.md`；文件不存在或零命中必须记录负结果，不能伪造历史经验。
  2. 命中条目时必须显式声明“本次差异是 X”或“仍适用，所以不重试旧路径”。
  3. Reflect 阶段按提名条件扫描并入库可复用教训。

### R2 阶段门

- **R2.1** 没需求文档不能进 Design。
- **R2.2** 没设计文档不能进 Tasks。
- **R2.3** 没 tasks.md 不能写代码；每项任务必须有可执行 verify。
- **R2.4** verify 未通过禁止标记完成。
- **R2.5** Review 的 Critical 项必须修复或显式接受。
- **R2.6** 测试失败自动重试不超过 3 轮，超限暂停并重审假设。

### R3 角色红线

- 设计者不写实现代码。
- 实现者不改需求/设计文档；发现需求问题时开新 feature。
- 审查者不修代码，只产出报告和修复 task。
- 同会话同时间只扮演一个角色；切换角色必须清窗。

### R4 提交与产物

- **R4.1** 每任务一次原子提交，格式 `<type>(scope): <task-id> <subject>`。
- **R4.2** 代码改动必须伴随测试改动。
- **R4.3** Bug 修复必须伴随回归测试。
- **R4.4** 没有 verify 证据不得声称完成。

### R5 测试纪律

- **R5.1** 测试用例必须从验收标准派生，禁止从实现派生。
- **R5.2** 禁止用 mock 屏蔽真实失败。
- **R5.3** 禁止删除或弱化测试来“修复”失败。

### R6 反幻觉

- **R6.1** 引用外部 API/字段名前必须检索验证存在性。
- **R6.2** 不确定事实必须明示待确认，禁止伪装已知。
- **R6.3** 不能假设代码可以工作，必须实际执行 verify。

### R7 范围控制

- **R7.1** 禁止悄悄扩大范围；超出 tasks.md 必须先更新计划或开新 feature。
- **R7.2** 同次提交不混入多个无关任务。

### R8 删除与公共接口门槛

- **R8.1** 删除不少于 5 行代码或修改公共 API 前，先检索全库调用点。
- **R8.2** 没有用户授权不执行删除。
- **R8.3** 检索必须考虑动态 import、反射和测试替身无法完整覆盖的边界。

## 执行投入层级（现有 Routing IR 的保守投影）

- **E0 只读**：明确只读任务；可定向查询、解释和引用证据，不允许写入。若同时触发安全/设备/发布高风险条件，E3 风险下限优先。
- **E1 轻量**：仅明确评估为 low risk、workspace-only 的局部实现。仍使用唯一 `docs/changes/<id>/` 变更合同；`requirements.md` 可缩至目标/非目标/验收，`design.md` 可缩至边界/影响/回滚，`tasks.md` 可缩至单个带 verify 的任务。三个文件仍存在；绝不省掉 R2 阶段门、基本 diff/test 或安全验证。当前未被路由显式判低风险的任务**不得自动使用 E1**。
- **E2 标准**：中风险或未知风险默认；按现有需求、设计、测试和 Spec/Quality 双维审查推进，必要时进行关键假设证伪。
- **E3 严格**：高风险、live-device、Flash/OTA、签名/权限、存储迁移、真实发布或明确升级效果的动作；独立证伪/负向测试/回滚/来源证据不可省。真实设备写入与发布仍需独立授权。
- 该等级是执行深度建议，不是 permission/approval/canonical change 的新事实来源。生产 matcher 可返回 `execution_effort` 与 `effort_basis`；`mutation_permission`、effect ceiling、live-device/release authorization 仍独立 fail-closed。匹配失败或风险不明不得用 E0/E1 绕过。
- 相同目标应优先删减冗余状态、适配器和 Agent 轮次，而不是新增平行 Skill 或 Gate；只有固定源码/模型/预算下的真实 A/B 证据能证明效率收益。

## 八阶段生命周期框架

> 来源：VibeFlow 子仓深度分析（2026-05-12）。权威设计记录同时见 `knowledge/L3-project/architecture-decisions/adr-001-8-phase-lifecycle.md` 和 `docs/workflows/lifecycle.md`。

```text
Spark → Design → Tasks → Build → Review → Test → Ship → Reflect
```

| 阶段 | 目标 | 输入 | 输出 | 门禁 |
|---|---|---|---|---|
| Spark | 需求澄清与价值验证 | 用户需求/问题描述 | 需求文档、价值评估 | 需求完整性检查 |
| Design | 技术方案设计 | 需求文档 | 设计文档、接口规范 | 三维评审通过 |
| Tasks | 合同化任务拆解 | 设计文档 | tasks.md、feature-list.json | 任务边界清晰 |
| Build | TDD 驱动开发 | tasks.md | 代码、单元测试 | 测试通过 |
| Review | 多视角代码审查 | 代码变更 | 审查报告 | 无阻塞性问题 |
| Test | 系统测试与 QA | 代码变更 | 测试报告 | 测试通过 |
| Ship | 发布部署 | 测试通过的代码 | 发布产物 | 发布门禁通过 |
| Reflect | 复盘沉淀 | 发布产物 | 复盘报告、经验教训 | 复盘完成 |

### 阶段转换

```yaml
transitions:
  spark_to_design:
    condition: 需求文档完成 && 价值评估通过
    gate: 需求完整性检查
  design_to_tasks:
    condition: 设计文档完成 && 三维评审通过
    gate: 设计评审门禁
  tasks_to_build:
    condition: tasks.md 完成 && 任务边界清晰
    gate: 任务合同检查
  build_to_review:
    condition: 代码完成 && 单元测试通过
    gate: 测试覆盖率检查
  review_to_test:
    condition: 审查通过 && 无阻塞性问题
    gate: 审查门禁
  test_to_ship:
    condition: 系统测试通过 && QA 签收
    gate: 测试门禁
  ship_to_reflect:
    condition: 发布成功 && 部署验证
    gate: 发布门禁
  reflect_to_spark:
    condition: 复盘完成 && 经验沉淀
    gate: 复盘门禁
```

小型变更仅在范围少于 3 个文件、不涉及架构或外部接口且用户明确指定快速模式时，允许采用 `Spark → Tasks → Build → Ship`。工作流状态持久化到 `.adk/state.json`，支持中断恢复、跨会话交接和状态查询。

## Gate 机制设计原则

### 显式委派的自动审核

Owner 可以通过明确指令委派自动推进和自动审核。仓库用 `.adk/review-policy.json` 及摘要绑定的原始授权记录声明范围；既有 review/archive 与 Harness 消费同一 typed review-evidence 校验器，不新增审批流程。未显式委派的仓库不默认启用。

独立 AI 审核者可在授权范围内完成最终 Spec/Quality 裁决；实现者和审核者身份必须不同，审核者保持只读并输出实际发现。记录真实授权、证据完成及审核时间，逐文件绑定来源和证据；政策或校验代码变化会使旧审核失效。仅传入 `--result pass`、修改日期或写入状态不能构成委派审核通过。

自动审核可完成源码、治理、已有测量或现场材料的审查，不生成缺失的测量、认证运行、现场事件或产品资格。真实证据不可得时，继续记录 evidence-blocked 和可执行的恢复入口，不重复索取已授予的执行或审核授权。

新增 Gate 前必须回答：

1. 是否 100% 可机械化；是则脚本化。
2. 是否必须稳定复现；是则状态机化。
3. 是否经常忘记且遗漏会造成风险；是则设置 Gate。
4. 是否更适合由 runtime、Skill 提示或项目工件承担；是则不新增 Gate。

前三项同时为“是”才新增 Gate。Gate 只拦截、不自动修复；通过标准必须客观；紧急绕过必须记录原因；所有绕过都要留下审计日志。

| Gate | 拦截内容 | 自动化程度 |
|---|---|---|
| 需求完整性检查 | 缺少需求文档 | 半自动 |
| 设计评审门禁 | 设计文档不完整 | 人工 |
| 任务合同检查 | 任务边界模糊 | 半自动 |
| 测试覆盖率检查 | 测试覆盖率不足 | 全自动 |
| 审查门禁 | 阻塞性问题未解决 | 人工 |
| 测试门禁 | 系统测试未通过 | 全自动 |
| 发布门禁 | 发布产物不完整 | 半自动 |
| 复盘门禁 | 复盘未完成 | 人工 |
