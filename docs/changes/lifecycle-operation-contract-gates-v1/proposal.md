# 变更提案：lifecycle-operation-contract-gates-v1

## 背景

跨模块变更若同时包含外部命令、异步完成、状态转换和共享资源，现有接口、审查和完成门禁虽分别覆盖部分要素，但没有同一份可追溯的生命周期契约。审查容易在后期提出 owner 或状态语义调整，进而把审查循环变成持续的方案重设计。

## 问题陈述（单问题）
- 本变更只解决一个明确问题：为受控生命周期操作建立通用的契约冻结、审查分流和完成验证规则。
- 触发证据：一次多仓状态/资源 owner 改造中，需求逐步演变为 owner、发布策略和退出语义重构，反复审查才暴露设计边界缺失。

## 目标
- 补强生命周期操作契约门禁

## 非目标

- 不增加任何业务领域、硬件、协议或平台专用 skill。
- 不改变 skill 路由、profile、manifest、权限模型或运行时行为。
- 不提供具体状态机实现或替代项目级 HIL 方案。

## Spec 链路检查
- requirements 基线：本提案的最小生命周期契约与非目标。
- design 决策：复用三个 core skill；生命周期契约仅在操作涉及状态、异步完成或共享资源时适用。
- tasks 追溯关系：T1 契约参考，T2 审查分流，T3 完成验证，T4 文本回归。

## 安装范围与依赖边界
- 安装范围（global-ready/project-bound）：global-ready core source。
- 依赖边界（脚本/数据/上下文）：仅 Markdown 资产与本仓现有 shell 文本断言；不增加运行时依赖。

## Prompt 回归证据计划
- before/after 对比输入：一个外部命令驱动、共享资源、异步完成的通用操作变更请求。
- 失败样例保留方式：缺 owner/state baseline 或审查要求改变终止语义时，必须得到 `needs-fix` 或 `design-change`，不允许普通修补通过。

## 收敛模式与退出条件
- 当前模式：execution。
- 退出条件：三个 skill 与引用闭环，文本回归和 strict validation 通过；若环境仅支持开发解释器，明确降级证据等级。

## 备选方案与取舍
- 方案 A：新增独立生命周期 skill。
- 方案 B：补强既有接口、审查、验证 skill，并以按需参考提供最小契约。
- 选型理由：选择 B，避免触发重叠、能力碎片化和平台/领域耦合。

## 风险与回退
- 主要风险是将普通同步接口误判为高负担流程。通过“仅状态、异步完成或共享资源操作适用”和 `not_applicable` 出口控制。回退为移除本 change 的 Markdown、参考和断言；不涉及运行时数据迁移。
