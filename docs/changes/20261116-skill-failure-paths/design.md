# 设计与执行边界

## 当前职责

主 Agent 负责需求/设计冻结、跨组取舍、证据整合与发布。三组只读审查者分别拥有通用 core、embedded core、optional 的完整人口；其清单与固定来源独立采集。产品方法实现由后续明确分配的实施者承担；最终审查者不修源码，自审不作独立裁决。

## 选取方法

对每个 Skill 先完整阅读当前主文件和资源，再判断实际触发、输入前提、正常路径、失败/恢复、输出证据以及上下文范围。外部 Skill 仅作候选来源，技术语义需由官方接口、实现或受控探针支持。已有方法充分时保留并写明理由；有不确定性时记录观察，不编造缺口。

发现的最小反例、修复范围和验收未冻结之前，不进入产品源码实施。应优先更正既有流程和示例，细节按需放入已有 reference；不将平台特定操作、未经审查的工具安装或隐式权限带入通用方法。

## 验证与证据

定向验证由需求派生，优先实际执行发布的示例或消费产物，区分目标错误、harness 错误和环境限制。复杂方法使用最小上下文的新消费者任务，保留输入/输出；不向消费者透露期望答案。独立源码审查与消费者验证是不同证据。

最终源码冻结后运行所需完整回归、strict、原有 Profile 预算和版本同步检查；只有新风险或既有门禁要求才重复验证。源修改、后续证据包装与平台发布事实分别绑定，不改写先前失败。

## 发布与回滚

存在实质方法修复时按现有版本管理入口前移版本，经普通 PR 和受保护合并，等待 exact-main 发布。实际 release 与 Root source-only 验证沿用现有实现，不新建发布协议。回滚通过新的受保护 PR 恢复先前版本的源码/依赖指针；不移动不可变 tag，不重写历史资格材料。

## 实施分工与写集

需求已冻结 F1–F5。core 实施者只修改 interface-contract-design、parallel-agent-governance 及其方法测试；embedded 实施者只修改 cmake-cross-build 及其方法测试；optional 实施者只修改 security-supply-chain、test-flakiness-triage、既有供应链 runbook 及相应方法测试。各自递增被修改 Skill 的版本，禁止修改本需求/设计或其他组源码。

主 Agent 串行整合 tests/test_skill_content.sh 的显式模块注册、整体版本同步、审查汇总与发布材料。实施者不改这些共享文件。既有预算很紧，新增内容优先替换有误/重复表达并保持语义；不删关键约束或放宽预算换取通过。

F1 使用原有 rg 能力改为路径候选输出，拒绝吞掉读取错误；不引入扫描依赖。F2 在现有日志与 TSV 已写入后停止约定中断状态，普通有界统计路径不变。F3 是构建方法与消费指导的改进，保留正常增量构建能力，不新增 toolchain 身份注册表或清理器；不能把 host 复现说成 SDK 强制防护。F4 保持未知字段拒绝并明确方言能力；提供最小可执行 schema 示例，避免平台专用模型输出 API 被当作通用 JSON Schema。F5 只修现有空模板的默认结果及证据说明。

## 方法验证安排

- Core：实际解析两个目标导出的 Completion Review；运行固定 schema/input 矩阵，保留错误组合与旧 draft 控制。
- Embedded：真实 CMake/Ninja 与本机编译器；记录 cache、CMakeSystem、实际编译命令和程序输出，含 --clean-first 控制；再安排最小上下文的新消费者执行任务。
- Optional：从当前发布文本提取真实 rg 命令与采样 helper，用合成文件/可控子进程验证输出、退出码和是否发生第二次调用。
- 完整回归、原预算、独立 Spec/Quality 与发布仍按原流程完成。消费者输出与确定性 host 试验分别解释，不拼接成模型 A/B 或设备证据。
