# 提交门禁设计

活动目标的提交门禁复用受管路由验证、用量快照、运行状态和工件契约。当前进度修订的 checkpoint 必须覆盖提交门禁要求的全部工件证据 ID。宿主应在登记证据前核对实际 Git 基线、待提交差异和检查结果。提交阶段的 `review` 指同一差异的源码审查，MR 评审状态仍由交付流程记录。

已完成目标继续走现有完成验证，提交额外受预算上限约束。最终、发布和应用门禁保留各自行为。回退时由消费方恢复原受管源码锁。

回放时使用 checkpoint 事件发生前已登记的证据计算 `verified`，原有事件和 journal 格式保持兼容。未通过的 checkpoint 保留修订号和证据 ID，重新验证后才能进入提交门禁。

同一容器中，未修改基线和最初候选的全量回归分别耗时 805.691 秒与 805.925 秒，均通过 102 项功能检查。基线发布契约与 Manifest 契约分别耗时 180.690 秒与 80.208 秒。Manifest 深度检查只遍历可能改变引号、转义或深度的字符。发布契约的变体使用快速压缩，保留各项归档内容、模式和来源验证。

发布契约和运行证据测试使用各自的临时夹具，在默认全量回归中与主序列重叠执行。发布升级夹具从发布源分发清单取输入，避免复制前景测试生成的报告。退出时回收异步测试进程组。结果按原注册顺序汇总，详细输出和遇错即停模式按原顺序执行。
