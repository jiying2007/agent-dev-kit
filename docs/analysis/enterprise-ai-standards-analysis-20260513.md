# 企业级AI团队研发规范 深度分析

**来源**: 企业级AI团队研发规范：平衡效率与质量的分级之道
**日期**: 2026-05-13

---

## 一、文章核心框架

### 1.1 解决的问题

> AI 介入研发后，最容易出现两种极端：
> - 流程太重，小改个文案也要写一堆文档
> - 完全不管，AI 一通乱改，老系统直接改崩

### 1.2 核心思路

```
分层阅读 → 分级介入 → 分模板执行
```

**一句话**: 不同复杂度，用不同方式，不搞一刀切。

---

## 二、三大策略深度分析

### 2.1 分层阅读：先看什么，后看什么

#### 新项目（从零搭建）

```
README → AGENTS.md → openspec/specs → 项目结构 → 当前任务
```

**关注点**:
- 领域边界在哪
- 每个模块该干什么
- 命名统一不统一
- 整体设计是否清晰

**核心原则**: 先把结构和规范立住

#### 老项目（维护/改造）

```
AGENTS.md → 现有代码 → 变更影响 → 当前任务
```

**关注点**:
- 千万别把现有系统改崩
- 理解现有约定
- 评估变更影响范围

**核心原则**: 先理解再动手

#### 微型改动

```
相关文件 → 当前任务
```

**核心原则**: 最小阅读，快速执行

#### adk 对比

| 场景 | 文章建议 | adk 现状 | 差距 |
|------|----------|----------|------|
| 新项目 | README→AGENTS→specs→结构→任务 | 无明确规则 | **需补强** |
| 老项目 | AGENTS→代码→影响→任务 | 无明确规则 | **需补强** |
| 微型改动 | 相关文件→任务 | 快速模式 | 已实现 |

### 2.2 分级介入：按复杂度匹配流程

#### Level 1: 简单任务

**特征**:
- 改文案、修 bug、小优化
- 影响范围 < 3 个文件
- 不涉及架构变更

**流程**:
```
需求 → 实现 → 验证
```

**产物**:
- 代码变更
- 简单说明

**时间**: < 1 小时

#### Level 2: 中等任务

**特征**:
- 新功能、重构模块
- 影响范围 3-10 个文件
- 涉及模块级变更

**流程**:
```
需求 → 设计 → 任务 → 实现 → 测试 → 审查
```

**产物**:
- 需求文档
- 设计文档
- 任务清单
- 代码变更
- 测试报告
- 审查报告

**时间**: 1-8 小时

#### Level 3: 复杂任务

**特征**:
- 架构变更、跨模块改动
- 影响范围 > 10 个文件
- 涉及系统级变更

**流程**:
```
需求 → 设计 → 评审 → 任务 → 实现 → 测试 → 审查 → 集成 → 发布
```

**产物**:
- 需求文档
- 设计文档
- 评审报告
- 任务清单
- 代码变更
- 测试报告
- 审查报告
- 集成报告
- 发布报告

**时间**: > 8 小时

#### adk 对比

| 级别 | 文章建议 | adk 现状 | 差距 |
|------|----------|----------|------|
| Level 1 | 需求→实现→验证 | 快速模式 (Spark→Tasks→Build→Ship) | 已实现 |
| Level 2 | 需求→设计→任务→实现→测试→审查 | 标准模式 (8 阶段) | 已实现 |
| Level 3 | 需求→设计→评审→任务→实现→测试→审查→集成→发布 | 完整模式 (8 阶段+门禁) | 已实现 |

### 2.3 分模板执行：6 套 AGENTS.md 模板

#### 模板 1: 全局模板

**适用**: 全公司统一原则

**内容**:
- 编码规范
- 提交规范
- 安全规则
- 质量门禁

#### 模板 2: 项目模板

**适用**: 每个服务自己的规则

**内容**:
- 项目特定约定
- 技术栈选择
- 架构约束
- 命名规范

#### 模板 3: Level 1 模板

**适用**: 简单任务

**内容**:
- 快速流程
- 最小产物
- 快速验证

#### 模板 4: Level 2 模板

**适用**: 中等任务

**内容**:
- 标准流程
- 完整产物
- 标准验证

#### 模板 5: Level 3 模板

**适用**: 复杂任务

**内容**:
- 完整流程
- 全部产物
- 严格验证

#### 模板 6: 紧急模板

**适用**: 热修复

**内容**:
- 最小流程
- 快速修复
- 事后补文档

#### adk 对比

| 模板 | 文章建议 | adk 现状 | 差距 |
|------|----------|----------|------|
| 全局模板 | 全公司统一原则 | AGENTS.md | 已实现 |
| 项目模板 | 项目特定规则 | CONTEXT.md | 已实现 |
| Level 1 模板 | 快速流程 | 快速模式 | 已实现 |
| Level 2 模板 | 标准流程 | 标准模式 | 已实现 |
| Level 3 模板 | 完整流程 | 完整模式 | 已实现 |
| 紧急模板 | 热修复流程 | 无 | **需补强** |

## 三、配套流程包分析

### 3.1 外部流程包样本

**来源定位**: 通用 AI 编程助手流程包，作为参考样本，不作为 adk 直接依赖。

**核心亮点**: 文档优先，提供可拆分的 `SKILL.md` 工作流入口。

**可借鉴工作流类型**:

| 工作流类型 | 适用场景 | 适配级别 |
|------------|----------|----------|
| 完整交付链路 | 非简单功能交付 | Level 2/3 |
| 探索后规格固化 | 需先探索再进入规范执行 | Level 2/3 |
| 轻量功能流程 | 无需重规格但需设计、计划、验证纪律 | Level 1 |
| 规格优先流程 | 只需先补齐 proposal、design、spec、tasks | Level 2 |

### 3.2 与 adk 的关系

| 维度 | 外部流程包样本 | adk |
|------|----------------|-----|
| 定位 | 通用工作流技能库 | 嵌入式工程资产包 |
| 范围 | 通用/全栈场景 | 嵌入式系统 |
| 格式 | `SKILL.md` 为主 | `SKILL.md` + `AGENTS.md` + `manifest.yaml` |
| 安装 | 复制到运行目录 | `devkit.sh install` / Codex handoff |

**核心洞察**: adk 可借鉴“显式启用、分级工作流、证据收口”的方法，但必须转换为嵌入式领域资产、profile 规则和本地验证门禁。

## 四、文章核心价值

### 4.1 解决的核心问题

1. **流程太重**: 小任务也要走完整流程
2. **完全不管**: AI 乱改代码
3. **一刀切**: 所有任务用同一套流程

### 4.2 提出的解决方案

1. **分层阅读**: 新项目 vs 老项目 vs 微型改动
2. **分级介入**: Level 1/2/3 按复杂度匹配
3. **分模板执行**: 6 套模板覆盖所有场景

### 4.3 落地效果

- 简单需求跑得飞快
- 复杂需求稳稳落地
- 团队用 AI，标准统一、心里有底

## 五、adk 可借鉴的模式

### 5.1 分层阅读规则（P0）

**新项目**:
```
README → AGENTS.md → CONTEXT.md → 项目结构 → 当前任务
```

**老项目**:
```
AGENTS.md → 现有代码 → 变更影响 → 当前任务
```

**微型改动**:
```
相关文件 → 当前任务
```

**落地方式**: 在 AGENTS.md 中增加分层阅读规则

### 5.2 紧急模板（P1）

**适用**: 热修复、线上事故

**流程**:
```
问题定位 → 快速修复 → 验证 → 发布 → 补文档
```

**产物**:
- 修复代码
- 验证结果
- 事后补文档

**落地方式**: 创建紧急 Profile

### 5.3 复杂度自动判断（P2）

**判断标准**:

| 维度 | Level 1 | Level 2 | Level 3 |
|------|---------|---------|---------|
| 文件数 | < 3 | 3-10 | > 10 |
| 架构影响 | 无 | 模块级 | 系统级 |
| 风险等级 | 低 | 中 | 高 |
| 时间预估 | < 1h | 1-8h | > 8h |

**落地方式**: 在 Spark 阶段自动判断复杂度

## 六、与 adk 现有架构的整合

### 6.1 与 8 阶段生命周期整合

```
Spark (分层阅读 + 复杂度判断)
    ↓
Design → Tasks → Build → Review → Test → Ship → Reflect
    ↓
根据复杂度选择 Level 1/2/3 流程
```

### 6.2 与 Profile 机制整合

```
Profile 选择
    ↓
根据复杂度选择 Level 1/2/3 Profile
    ↓
加载对应的 AGENTS.md 模板
```

### 6.3 与知识分层架构整合

```
knowledge/
├── L0-toolchain/        # 工具链配置
├── L1-general-tech/     # 通用技术
├── L2-domain/           # 业务领域
├── L3-project/          # 项目上下文
│   ├── reading-order.md # 分层阅读规则（新增）
│   └── complexity.md    # 复杂度判断规则（新增）
└── L4-session/          # 会话上下文
```

## 八、总结

这篇文章的核心价值在于：

1. **分层阅读**: 解决 AI 盲目乱改问题
2. **分级介入**: 解决流程一刀切问题
3. **分模板执行**: 解决团队用法不统一问题

**核心洞察**: "不同复杂度，用不同方式，不搞一刀切"——这与我们 adk 的"快速模式"理念完全一致，但文章提供了更完整的分层阅读和复杂度判断机制。

**adk 需要补强的**:
1. 分层阅读规则（新项目 vs 老项目）
2. 紧急模板（热修复流程）
3. 复杂度自动判断机制

**adk 已经具备的**:
1. 分级介入（快速模式/标准模式/完整模式）
2. 分模板执行（10 个 Profile）
3. 质量门禁（Gate 机制）
