# 5.0.0-rc.1 平台控制面迁移

## 迁移范围

`5.0.0-rc.1` 是平台控制面候选，不是 `4.0.0` 的原位兼容升级。它包含以下破坏式边界：

- core Profile 移除领域专属资产；嵌入式能力改由显式 `embedded-fullstack` Profile 选择。
- target contract 从 v1 切换到 v2；旧 contract 不进入 active loader。
- routing 和 Workflow 使用 IR v2；Runtime Control 的 intake、policy 和 decision 使用 v2 合同。
- Trace Summary、Evidence Graph、Run Evidence Composition、Effect Comparison 和 Agent Value receipt 成为机器证据入口。
- privacy reference 和 native target conformance receipt 采用显式、可验证、fail-closed 的引用边界。

manifest 数据格式仍为 `schema_version: 4.0.0`。该字段标识 manifest schema，不等同于产品发布版本；产品版本为 `5.0.0-rc.1`。

## 升级步骤

1. 保留当前 `4.0.0` source、artifact、checksum、安装 receipt 和受管资产 hash，作为完整回滚锚点。
2. 在候选源码运行 strict validate、doctor、quick/full test、release check 和 source distribution build。
3. 重新生成目标导出、安装 plan 和 receipt；不得复用 v1 target contract、旧 routing 输出或旧 Runtime Control state。
4. 对每个声明支持的 direct target 分别执行 discovery、load、trigger、permission smoke，并保留 runtime/version 与命令摘要。
5. 另建 5.x campaign/ledger；不得改写 4.x append-only 历史。
6. R6 双运行时 campaign 与 R10 field evidence 未通过前，只能维持 candidate 状态。

## 调用方迁移

- 显式选择 Profile；不要假设 core 自动包含嵌入式资产。
- 按 v2 schema 重新生成 target contract、Workflow IR 和 Runtime Control input/output。
- 每次运行显式产生 trace/receipt，并通过 Run Evidence Composition 聚合；不要从日志文本推断成功。
- Agent/Skill 价值判断必须声明评估窗口、覆盖率和 trust level；样本不足时返回 insufficient evidence。

## 回滚

回滚只能恢复完整的 `4.0.0` source/artifact/receipt/managed hashes。禁止把 4.x module、contract、state 或导出文件局部混入 5.x 候选。没有 checksum 绑定的 `4.0.0` artifact 时，不得声称升级/回滚演练已完成。

## 完成边界

本迁移文档和本地候选 build 只证明 source-ready/release-candidate-ready。它们不证明 tag、远端发布、source-to-live、真实双运行时 campaign、30 天 field pilot 或 M5 certification 已完成。
