# 3.1.0-rc.3 合同加固迁移

## 适用范围

本文面向从 `3.1.0-rc.2` 升级到 `3.1.0-rc.3` 的维护者。`rc.3` 仍是 prerelease；它修复性能、Harness readiness、manifest schema、安装声明和本地 CI 替代验证的跨层漂移，不代表 Software M5 certification 或 terminal maturity。

## 兼容性变化

| 项目 | rc.2 | rc.3 |
|---|---|---|
| Python | 3.8+ 声明 | 3.11+ 发布支持基线 |
| 运行依赖 | 宽松 PyYAML / 旧 jsonschema | `PyYAML==6.0.3`、`jsonschema==4.26.0` |
| install mode | manifest 曾声明 symlink | JSON/YAML/schema/CLI 统一 copy-only |
| nested manifest objects | 部分只验证 object | typed、required、拒绝未知字段 |
| Harness readiness | 启发式权限文本可产生假阳性 | 结构化权限边界、freshness 与 ownership fail-closed |
| 本地 CI 替代证据 | 无统一入口 | Python 3.11/3.12、非 root、离线 gates、独立 audit |
| source distribution | 未携带新 ownership metadata | 显式包含 `OWNERS` 与 `.adk/harness-readiness.json` |

direct target 路径、plan v2、receipt v3、copy transaction 与 rollback 语义不变。三个 direct target 继续保持 `experimental`。

## 升级步骤

1. 保留 checksum 已核验的 rc.2 source artifact，作为升级和 fallback 锚点。
2. 将执行环境升级到 Python 3.11 或 3.12，并安装锁定的运行依赖。
3. 对自定义 manifest 执行 `bash scripts/devkit.sh validate --strict`；修正错误类型、缺失必填字段和未知 nested 字段。确需保留的产品扩展迁移到顶层 `x-<name>` namespace。
4. 删除任何 symlink install 配置，使用 copy plan/apply/rollback；不要把历史声明当作已支持行为。
5. 执行 `bash scripts/devkit.sh doctor --strict`、full regression、security、release check 和 rc.2 → rc.3 rehearsal。
6. 远端 CI 暂时不可用时，可按 `docs/runbooks/local-ci-parity.md` 生成时限内的本地替代证据；该证据不能解释为远端 provenance、发布认证或现场认证。

## 回滚锚点

- rc.2 artifact、SHA256 sidecar 和 rc.2 manifest digest 必须保留并独立核验。
- rc.3 rehearsal 必须证明候选安装、receipt 校验、候选回滚和 rc.2 fallback restore 全部通过。
- 回滚到 rc.2 会重新引入 Python/依赖、schema、symlink 声明和 readiness 假阳性风险，只能作为短期恢复，不得继续声明 rc.3 的门禁能力。
- 不自动创建 tag、发布远端制品、写用户运行目录或执行付费 runtime campaign。

## 未关闭边界

本地 source/test/rehearsal 不能替代远端 CI 与 attestation、Claude/Codex 双 runtime campaign、独立真实仓、第二位 human operator、30 天 field pilot 和最终 `3.1.0` eligibility。任一证据缺失时，`software_m5_certified` 与 `terminal_mature` 必须保持 false。
