# 紧急工作流模板 (Emergency Workflow Template)

> **使用场景**: 生产环境 P0/P1 级故障需要紧急修复，标准流程来不及执行时使用。
> **状态机**: emergency-response → emergency-fix → emergency-verify → emergency-release → emergency-review
> **核心原则**: 速度优先，但必须保留事后复盘。审查和文档可后补，但不可跳过。

---

## 工作流概述

> **何时使用**: 生产环境 P0/P1 级故障需要紧急修复时使用。正常开发流程请改用 standard-workflow-template。

紧急工作流是标准工作流的精简版，用于应对生产环境紧急故障。
省略了 Propose 阶段的详细设计，压缩了审查流程，但增加了事后复盘环节。
整个流程目标耗时: P0 故障 ≤ 4 小时，P1 故障 ≤ 24 小时。

---

## Stage 1: Emergency Response (紧急响应)

**目的**: 快速确认故障范围、影响和初步应对措施。

**Entry Criteria**:
- [ ] 生产环境告警触发或用户报告 P0/P1 故障
- [ ] 值班人员已确认

**执行步骤**:
1. 确认故障现象和影响范围
2. 评估故障等级 (P0: 全面不可用 / P1: 核心功能受损 / P2: 部分功能受损)
3. 通知相关团队和管理层
4. 创建紧急变更工单 (CHG-EMERGENCY-YYYY-NNN)
5. 初步判断根因方向（代码/配置/基础设施/外部依赖）
6. 决定是否需要立即回滚（如回滚可解决，直接执行回滚）

**产出物**:
- 故障确认报告（简要）：现象、影响范围、初步根因、紧急程度
- 沟通记录

**Exit Criteria**:
- [ ] 故障已确认并评估等级
- [ ] 相关人员已通知
- [ ] 初步根因方向已明确
- [ ] 已决定修复方向（修复 or 回滚）
- [ ] 响应时间 ≤ 30 分钟

---

## Stage 2: Emergency Fix (紧急修复)

**目的**: 开发并提交最小范围的修复代码。

**Entry Criteria**:
- [ ] Emergency Response 阶段已确认需要代码修复（非回滚）
- [ ] 根因已基本定位
- [ ] 修复方案已确定（可以是简要方案）

**执行步骤**:
1. 从主干创建 hotfix 分支
2. 编写最小范围修复代码（最小改动原则）
3. 编写关键路径的单元测试
4. 本地验证修复有效
5. 提交代码并触发 CI
6. 如修复失败，重新评估方案（可能转为回滚）

**产出物**:
- hotfix 分支代码
- 关键测试用例

**Exit Criteria**:
- [ ] 修复代码已提交
- [ ] CI 构建通过
- [ ] 本地验证修复有效
- [ ] 修复范围最小化（只改必须改的）
- [ ] 修复耗时 ≤ 2 小时 (P0) 或 ≤ 12 小时 (P1)

---

## Stage 3: Emergency Verify (紧急验证)

**目的**: 快速验证修复不会引入新的问题。

**Entry Criteria**:
- [ ] Emergency Fix 阶段 CI 构建通过
- [ ] 测试环境可用

**执行步骤**:
1. 在 Staging 环境部署修复
2. 运行关键路径测试（不要求全量）
3. 手动验证故障已修复
4. 检查是否有明显的回归问题
5. 如有条件，执行冒烟测试
6. 记录测试结果（简要报告）

**产出物**:
- 简要测试记录（非完整 test-report，事后补全）
- 验证确认

**Exit Criteria**:
- [ ] 故障在 Staging 环境已修复
- [ ] 关键路径测试通过
- [ ] 无明显回归问题
- [ ] 验证耗时 ≤ 30 分钟 (P0) 或 ≤ 2 小时 (P1)

---

## Stage 4: Emergency Release (紧急发布)

**目的**: 将修复部署到生产环境。

**Entry Criteria**:
- [ ] Emergency Verify 阶段已确认修复有效
- [ ] 发布已获口头授权（不需要完整签核）

**执行步骤**:
1. 确认发布窗口（紧急情况下通常立即发布）
2. 合入 hotfix 分支到主干
3. 部署到生产环境
4. 验证生产环境故障已恢复
5. 监控关键指标 15-30 分钟
6. 确认服务稳定后通知相关团队
7. 如部署失败，立即执行回滚

**产出物**:
- 生产环境修复部署完成
- 服务恢复确认

**Exit Criteria**:
- [ ] 修复已部署到生产环境
- [ ] 故障已确认恢复
- [ ] 监控指标正常（无异常波动）
- [ ] 相关团队已通知恢复
- [ ] 如失败，回滚已完成

---

## Stage 5: Emergency Review (紧急复盘)

**目的**: 事后补齐文档、审查和复盘，从故障中学习。

**Entry Criteria**:
- [ ] Emergency Release 阶段已完成，服务已恢复
- [ ] 团队有精力进行复盘（通常在恢复后 24-72 小时内）

**执行步骤**:
1. 补全 design-spec（如修复涉及设计变更）
2. 补全 test-report（补全测试用例和覆盖率报告）
3. 补全 review-report（对 hotfix 代码进行正式审查）
4. 补全 approval-document（补签核）
5. 编写故障复盘报告 (Post-Mortem):
   - 故障时间线
   - 根因分析 (Root Cause Analysis)
   - 影响范围和持续时间
   - 修复措施
   - 预防措施 (Action Items)
6. 更新监控和告警规则
7. 归档所有产出物
8. 跟踪 Action Items 完成

**产出物**:
- 故障复盘报告 (Post-Mortem)
- 补全的文档集（design-spec, test-report, review-report, approval）
- Action Items 列表

**Exit Criteria**:
- [ ] 所有文档已补全
- [ ] 故障复盘报告已完成
- [ ] Action Items 已分配并有截止日期
- [ ] 监控/告警已更新（如需要）
- [ ] 所有产出物已归档
- [ ] 复盘会议已召开

## 与标准工作流的对比

| 维度 | 标准工作流 | 紧急工作流 |
|------|-----------|-----------|
| 设计文档 | 事前完成 | 事后补全 |
| 代码审查 | 事前完成 | 事后审查 |
| 测试覆盖 | 全量测试 | 关键路径测试 |
| 审批签核 | 正式签核 | 口头授权 + 事后补签 |
| 复盘 | 可选 | 必须 |
| 文档归档 | 事前 | 事后 72h 内补全 |
| 目标耗时 | 无限制 | P0 ≤ 4h, P1 ≤ 24h |

## 回退/降级规则

- Emergency Response 阶段判断可回滚解决 → 直接执行回滚，跳过 Fix/Verify
- Emergency Fix 阶段修复太复杂 → 转为先回滚恢复服务，后续按标准流程修复
- Emergency Verify 阶段发现回归 → 返回 Emergency Fix
- Emergency Release 部署失败 → 立即回滚，返回 Emergency Fix
