## 2. 用户故事（User Stories）

### 2.1 故事拆分规则

拆分用户故事时遵循以下原则：
1. **INVEST 原则**: Independent（独立）、Negotiable（可协商）、Valuable（有价值）、Estimable（可估算）、Small（足够小）、Testable（可测试）
2. **纵向切分**: 每个故事应端到端交付价值，避免按技术层横向切分
3. **单次迭代**: 一个故事应在单个迭代内完成（建议 ≤ 5 故事点）
4. **单一角色**: 一个故事只描述一个角色的行为

### 3.1 验收条件编写规范

每个用户故事必须包含至少 2 条验收条件，采用 Given/When/Then 格式：

```
Given [前置条件]
When  [触发操作]
Then  [预期结果]
```

| 优先级 | 含义 | 说明 |
|--------|------|------|
| P0 | 必须有 | 没有此功能产品无法发布 |

| 2 | 4h ~ 1d | 中等改动，涉及单模块 |
| 3 | 1d ~ 2d | 较复杂，涉及模块间交互 |

## 7. 示例

### 示例：OTA 固件升级功能

#### 用户角色
- **角色名称**: 嵌入式固件工程师
- **描述**: 负责 IoT 设备固件开发与维护，需要通过 OTA 方式远程更新设备固件
- **痛点**: 当前每次固件更新需现场烧录，人力成本高，无法快速修复线上问题

#### 用户故事
- **US-001**: 作为固件工程师，我想要通过 HTTP 下载新固件包，以便实现远程固件更新
  - 优先级: P0 | 故事点: 5
- **US-002**: 作为固件工程师，我想要在升级前校验固件签名，以便防止恶意固件注入
  - 优先级: P0 | 故事点: 3
- **US-003**: 作为固件工程师，我想要在升级失败时自动回滚到上一版本，以便保证设备可用性
  - 优先级: P0 | 故事点: 3

#### 验收条件 (US-001)
- AC-1: Given 设备联网且服务器有新版本, When 触发 OTA 检查, Then 返回最新版本号和下载 URL
- AC-2: Given 获得下载 URL, When 开始下载, Then 固件完整保存到临时分区且 MD5 校验通过
- AC-3: Given 下载中断, When 网络恢复, Then 支持断点续传

### 8.1 术语表

| 术语 | 定义 |
|------|------|
| User Story | 用户故事，描述用户需求的简短叙述 |
| Acceptance Criteria | 验收条件，定义故事完成的标准 |
| Story Point | 故事点，衡量故事复杂度的相对单位 |
| Persona | 用户角色，目标用户的典型代表 |
| Epic | 史诗，一组相关用户故事的集合 |

**模板使用说明**：
1. 使用此模板将 PRD 拆解为可执行的用户故事
2. 每个故事必须包含验收条件（Given/When/Then 格式）
3. 故事点估算参考团队历史速度
4. 依赖关系需在 handoff 前识别并标注
5. 测试用例需与验收条件一一对应
6. 保持格式一致性，更新状态字段
